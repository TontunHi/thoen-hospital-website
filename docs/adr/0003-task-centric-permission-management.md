# 3. การปรับโครงสร้างระบบกำหนดสิทธิ์แบบยึดตามภารกิจงาน (Task-Centric Permission Management System)

Date: 2026-10-09

## สถานะ (Status)
ยอมรับแล้ว (Accepted)

## บริบท (Context)
เดิมระบบกำหนดสิทธิ์การเข้าใช้งานและสิทธิ์ในกล่องงานที่หน้า `/member/settings` ใช้รูปแบบ **User-Centric Matrix** (แสดงรายชื่อบุคลากรทั้งหมด 100+ คน แล้วติ๊ก Checkbox สิทธิ์รายคน/รายโมดูล) 

ปัญหาที่พบคือ:
1. **ความยากในการบริหารจัดการตามงาน:** เมื่อมีงานประเภทหนึ่ง (เช่น "งานขอสื่อประชาสัมพันธ์" หรือ "งานซ่อมไอที") ผู้ดูแลระบบไม่สามารถมองเห็นภาพรวมได้ทันทีว่า "ใครบ้างที่รับผิดชอบงานนี้", "ใครเป็นคนตรวจรับ/อนุมัติ", และ "ใครเป็นคนปฏิบัติงาน/ช่าง"
2. **ความเสี่ยงในการมอบสิทธิ์ผิดพลาด:** การติ๊กสิทธิ์แบบแยกรายคนรายช่องทำให้ง่ายต่อการสับสนระหว่างสิทธิ์อนุมัติ (Approve) กับสิทธิ์ปฏิบัติการ (Edit/Do)
3. **การรองรับความยืดหยุ่นในโรงพยาบาล:** บางงานต้องการกำหนดสิทธิ์ตามตำแหน่งหลัก (เช่น นักประชาสัมพันธ์ทุกคน) ในขณะที่บางงานต้องการระบุตัวบุคคลเฉพาะกิจ (กรรมการ/ผู้ได้รับมอบหมายรายคน)

## การตัดสินใจ (Decision)

1. **สถาปัตยกรรม Task-Centric Permission Model:**
   - เปลี่ยนกระบวนทัศน์การตั้งค่าจาก "เลือกคน -> ให้สิทธิ์" เป็น **"เลือกงาน -> กำหนดผู้รับผิดชอบตามบทบาท (Task-Centric)"**
   - จัดหมวดหมู่งานออกเป็น 2 กลุ่มหลัก:
     1. **งานบริการและกล่องงาน (Workflow Tasks):** เช่น งานขอสื่อประชาสัมพันธ์ (`MEDIA_REQUEST`), ซ่อมคอมพิวเตอร์/ไอที (`IT_REPAIR`), ซ่อมบำรุงทั่วไป (`GENERAL_REPAIR`), ซ่อมเครื่องมือแพทย์ (`MEDICAL_REPAIR`), กล่องงานกลาง (`INBOX_CENTRAL`)
     2. **ระบบบริหารและกำกับดูแล (System & Governance Modules):** เช่น งานสลิปเงินเดือน (`SALARY`), งานพัสดุและสถานที่ (`FACILITY_ASSET`), งานสารบรรณหนังสือส่งออก (`OUTGOING_DOC`), ชมรมจริยธรรม (`ETHICS`), การประเมิน ITA (`ITA`), เอกสาร RDU (`RDU`), ข่าวสารและสไลด์ (`NEWS`)

2. **โครงสร้าง 4 บทบาทมาตรฐาน (4 Canonical Role Archetypes per Task):**
   ในแต่ละงานจะแบ่งบทบาทผู้รับผิดชอบเป็น 4 ระดับ:
   - 👁️ **View (ผู้ดูงาน):** สิทธิ์ดูและติดตามงานทั้งหมดในสายงานนั้น (Read-only)
   - 🛠️ **Edit / Do (ผู้ปฏิบัติงาน):** ช่าง/ผู้ผลิตสื่อ/เจ้าหน้าที่ปฏิบัติการ มีสิทธิ์กดรับงาน, บันทึกผล, แก้ไขข้อมูล
   - ✍️ **Approve (ผู้อนุมัติ):** ผู้บริหาร/หัวหน้างาน มีสิทธิ์ลงนามอนุมัติและตรวจรับงาน (Approve-only)
   - 👑 **Manage (ผู้ดูแลงาน):** หัวหน้าสายงาน/ผู้ดูแลระบบงาน มีสิทธิ์มอบหมายงาน, จัดคิว และดูแลภาพรวม

3. **กลไก Hybrid Assignment (รายบุคคล + ตามตำแหน่งงาน):**
   - รองรับการเพิ่มผู้รับผิดชอบแบบ **รายบุคคล (Member-based)** โดยค้นหาชื่อ-สกุลจากฐานข้อมูล
   - รองรับการเพิ่มผู้รับผิดชอบแบบ **ตามตำแหน่ง (Position-based)** โดยดึงตำแหน่งงานที่มีอยู่จริงในฐานข้อมูลบุคลากรของ รพ.เถิน มาให้เลือก
   - แสดง Avatar / Badge แยกระหว่างบุคคลและตำแหน่งงานอย่างชัดเจน พร้อมปุ่มปลดสิทธิ์ (Revoke) ได้ทันที

4. **Zero-Downtime Data Mapping & Compatibility:**
   - เบื้องหลังระบบจะทำการแปลง Task & Role เป็น Permission Keys เดิมที่บันทึกลงในตาราง `member_permissions` และ `position_permissions`
   - ทำให้ระบบความปลอดภัย, API RBAC, `taskPermissionResolver.ts` และ `taskInboxService.ts` ทำงานร่วมกันได้อย่างสมบูรณ์แบบโดยไม่ต้อง Migrate โครงสร้างฐานข้อมูลใหม่

5. **ส่วนติดต่อผู้ใช้งาน (UI/UX & Master-Detail Layout):**
   - **Main Workspace (Task-Centric View):** ฝั่งซ้ายเป็นเมนูเลือกงาน (Task Navigator) จัดกลุ่มชัดเจน ฝั่งขวาเป็นกระดาน 4 Roles แสดงรายชื่อผู้ได้รับสิทธิ์แบบการ์ด/ชิป และปุ่ม `+ เพิ่มผู้รับผิดชอบ`
   - **Member Inspector Tab:** แท็บสำหรับค้นหารายชื่อบุคลากรรายบุคคล เพื่อดูสรุปว่าเจ้าหน้าที่คนนั้นมีสิทธิ์ในงานใดบ้างในโรงพยาบาล
   - **Feature Toggles Tab:** สวิตช์ควบคุมการเปิด/ปิดโมดูลระบบบริการต่างๆ

6. **Instant Auto-Save with Visual Feedback:**
   - การเพิ่ม/ลบผู้รับผิดชอบจะบันทึกลงฐานข้อมูลแบบทันที (Instant Auto-Save) พร้อมแสดง Notification Toast ยืนยันผลการทำงาน

## ผลกระทบ (Consequences)

### ผลเชิงบวก (Positive):
- ผู้ดูแลระบบสามารถมองเห็นโครงสร้างผู้รับผิดชอบของแต่ละงานได้อย่างชัดเจน ครบถ้วน ถูกต้องตามสายการปฏิบัติงานจริง
- ลดความผิดพลาดในการมอบหมายสิทธิ์ซ้ำซ้อนหรือมอบสิทธิ์ผิดระดับ
- สะดวก รวดเร็ว และลดเวลาในการตั้งค่าสิทธิ์สำหรับงานใหม่หรือเมื่อมีการโยกย้ายตำแหน่ง

### สิ่งที่ต้องระวัง / ข้อจำกัด (Trade-offs):
- เมื่อมีการแก้ไขสิทธิ์ตามตำแหน่ง ผู้ใช้ทุกคนในตำแหน่งนั้นจะได้รับสิทธิ์ตามที่กำหนดโดยอัตโนมัติ ซึ่งต้องมีการแสดงข้อความเตือนให้ Admin ทราบชัดเจนใน UI
- ต้องตรวจสอบให้แน่ใจว่า API อัปเดตสิทธิ์รองรับการบันทึกทั้งระดับ `member_permissions` และ `position_permissions` อย่างถูกต้อง
