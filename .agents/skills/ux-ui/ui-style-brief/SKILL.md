# สไตล์ดีไซน์ UI ของเรา และวิธีบรีฟ AI

ผู้ใช้เป็นนักพัฒนาระบบสื่อสารภายในโรงพยาบาล (NestJS backend, PWA frontend) ตอบเป็นภาษาไทยเสมอ เว้นแต่ผู้ใช้ใช้ภาษาอื่น
ข้อมูลทางเทคนิคที่มีโครงสร้างให้ใช้ตารางธรรมดา

## สองโหมด

| โหมด | ใช้เมื่อ | ทำอะไร |
|---|---|---|
| A. ออกแบบเอง | ผู้ใช้ส่งภาพหน้าเดิม หรือสั่งให้ออกแบบ/ปรับหน้า | ทำตามขั้นตอนด้านล่าง ส่งต้นแบบที่กดได้ + ไฟล์ spec `.md` |
| B. เขียน brief | ผู้ใช้ขอ prompt / brief / skill สำหรับสั่ง AI | กรอก `references/brief-template.md` ด้วยบริบทจริงจากบทสนทนา อย่าให้เทมเพลตเปล่า |

ถ้าไม่ชัดว่าโหมดไหน ให้ทำโหมด A ถ้ามีภาพหรือชื่อหน้า และโหมด B ถ้าไม่มีหน้าให้ออกแบบ

## หลักการ 7 ข้อ (ห้ามละเมิดโดยไม่บอกเหตุผล)

1. **ข้อมูลมาก่อนการตกแต่ง** ผู้ใช้เปิดหน้าเพื่อทำอะไรสักอย่าง จัดลำดับตามนั้น ไม่ใช่ตามความสวย
2. **ไม่มีไอคอนตกแต่ง** ค่าเริ่มต้นคือไม่ใส่ไอคอนเลย ไอคอนได้เฉพาะกรณีที่ไม่มีที่ว่างสำหรับข้อความและความหมายสากลชัดเจน (เช่น ปุ่มปิด) ถ้าไม่แน่ใจ ให้ตัดออก ห้าม emoji ในส่วนติดต่อผู้ใช้
3. **สีสื่อความหมาย 1 สี = 1 ความหมาย** สี accent หลักใช้กับสิ่งที่เลือกอยู่และปุ่มหลักเท่านั้น สีอื่นเป็นพื้นอ่อน + ตัวอักษรเข้มโทนเดียวกัน มีตัวอักษรบอกความหมายกำกับเสมอ รายละเอียดใน `references/tokens.md`
4. **หนึ่งหน้า หนึ่งการกระทำหลัก** ในแถวรายการ: ปุ่มหลักไม่เกิน 1 + ลิงก์ข้อความ 1 ส่วนที่เหลือย้ายไปหน้ารายละเอียดหรือกดที่ชื่อ
5. **ตัดของซ้ำ** ข้อมูลที่เหมือนกันทุกแถว (ป้ายสถานะ, ปีงบ, ชื่อผู้จัด) ย้ายไปตัวกรองหรือหน้ารายละเอียด ไม่แสดงซ้ำ
6. **แก้ปัญหาโครงสร้างจริง ไม่ใช่แค่ทาสี** เช่น โพเดียม 3 ช่องที่พังเมื่อคะแนนเท่ากัน ให้ออกแบบรองรับกรณีขอบ (tie, ว่าง, ชื่อยาว, ข้อมูลเยอะ)
7. **ไม่ดู AI slop** ตรวจด้วยรายการใน `references/review-checklist.md` ก่อนส่งทุกครั้ง

## ขั้นตอนโหมด A

1. **เข้าใจหน้า** ระบุ: ใครใช้, ใช้ทำอะไร, อุปกรณ์หลัก, ข้อมูลและฟีเจอร์ที่ต้องคงไว้ ดึงจากภาพให้มากที่สุดก่อน ถ้าขาดข้อมูลสำคัญจริงค่อยถาม ไม่เกิน 1 คำถาม
2. **หาปัญหาของหน้าเดิม** เขียนเป็นข้อ ๆ ที่ตรวจสอบได้ ("อันดับ 3 ว่างเพราะอันดับ 1 มี 3 คน") ไม่ใช้คำกว้าง ๆ ("ไม่สวย")
3. **รอบตัด (subtraction pass)** ลิสต์สิ่งที่จะตัดพร้อมเหตุผล ก่อนเพิ่มอะไรใหม่
4. **จัดลำดับ** ข้อมูลระดับ 1 (ต้องเห็นทันที), 2 (เห็นเมื่อสนใจ), 3 (ย้ายไปหน้ารายละเอียด)
5. **เลือก token** จาก `references/tokens.md` แล้วดู `references/components.md` สำหรับตาราง แท็บ ฟอร์ม ชิป ปุ่ม สถานะ
6. **สร้างต้นแบบที่กดได้** ใช้ข้อมูลจริงจากภาพ ทำให้แท็บ ค้นหา ตัวกรอง ทำงานจริง ส่วนที่ไม่มีข้อมูลจริงให้ใส่ placeholder ที่ติดป้ายชัด เช่น `[ชื่อกิจกรรมที่เสร็จสิ้น 1]` ห้ามแต่งตัวเลขหรือชื่อให้ดูจริง
7. **ตรวจ** ด้วย `references/review-checklist.md` แก้ให้ผ่านก่อนส่ง
8. **เขียน spec `.md`** ตามโครงใน `references/spec-template.md` ทุกครั้ง แม้ผู้ใช้ไม่ได้ขอซ้ำ (ผู้ใช้ขอทุกหน้าที่ผ่านมา)
9. **ตอบสั้น ๆ** ตาราง "ของเดิม → ของใหม่" แล้วหัวข้อ "ควรรู้" ที่บอกตรง ๆ ว่าอะไรเป็น placeholder, อะไรไม่ได้เชื่อมระบบจริง, อะไรยังไม่ได้ออกแบบ, และสิ่งที่ยังไม่ได้เปิดดูผลลัพธ์จริง

## เมื่อผู้ใช้ขอแก้ทีละรอบ

- แก้เฉพาะส่วนที่บอก อย่าเปลี่ยนโครงสร้างที่ไม่ได้พูดถึง
- ถ้าผู้ใช้บอกกว้าง ๆ ("ดูเข้าใจยาก", "ขอสีเยอะขึ้น") ให้ถามตัวเองก่อนว่าปัญหาจริงคืออะไร (ขาดการแยกประเภท? ลำดับสำคัญไม่ชัด? ศัพท์เข้าใจยาก?) แล้วแก้ที่ต้นเหตุ ไม่ใช่เพิ่มสีสุ่ม
- อัปเดต spec `.md` ให้ตรงกับต้นแบบเสมอ อย่าปล่อยให้ขัดกัน

## ภาษาและข้อความในหน้า (microcopy)

- ภาษาไทยเป็นหลัก ศัพท์ที่คนในโรงพยาบาลใช้จริงมาก่อนศัพท์ทับศัพท์
- ปุ่มขึ้นต้นด้วยคำกริยา สั้น ตรงงาน: "ลงทะเบียนล่วงหน้า", "สร้างกิจกรรมใหม่" ไม่ใช้ "ตกลง" ลอย ๆ
- ใช้คำเดียวต่อหนึ่งแนวคิดทั้งหน้า (อย่าสลับ "ภารกิจ", "งาน", "task")
- สถานะว่างต้องบอกว่าทำอะไรต่อได้ ("ยังไม่มีกิจกรรมที่คุณลงทะเบียนไว้")
- ปี พ.ศ. และรูปแบบวันที่ไทย (1 พ.ย. 2569) ตัวเลขใช้ `tabular-nums` ในตาราง

## ส่งมอบ

| สิ่งที่ส่ง | รายละเอียด |
|---|---|
| ต้นแบบที่กดได้ | หน้าเว็บที่ใช้งานได้จริงในเบราว์เซอร์ ใช้ Design/Artifact ที่ระบบมีให้ก่อน |
| spec `.md` | โครงตาม `references/spec-template.md` ใช้ตารางเป็นหลัก |
| ข้อเสนอฟิลด์ API | ฟิลด์ที่หน้านี้ต้องใช้ เพื่อให้ฝั่ง NestJS เตรียมได้ |
| ถ้าผู้ใช้ขอโค้ด | ถามหรือเดา stack จากบริบท ถ้าไม่รู้ให้ส่ง CSS variables ที่ย้ายไป Tailwind/อื่นได้ง่าย |

## โหมด B: เขียน brief

1. อ่าน `references/brief-template.md`
2. กรอกด้วยบริบทจริง: ชื่อหน้า, ปัญหาเดิม, ข้อมูลที่ต้องคงไว้, ประเภทข้อมูลที่ต้องแยกด้วยสี, stack
3. ใส่ข้อห้ามของสไตล์เรา (ไอคอน, gradient, ขอบสีซ้ายการ์ด ฯลฯ) ทุกครั้ง เพราะเป็นสิ่งที่ AI ชอบใส่เอง
4. ปิดท้ายด้วยตารางสั้น ๆ ว่าแต่ละประโยคใน brief กันปัญหาอะไร
5. ถ้าขอ brief สำหรับ "เพิ่มสี" ให้เน้นกฎ 1 สี = 1 ความหมาย และให้ระบุประเภทข้อมูลที่ต้องแยก
